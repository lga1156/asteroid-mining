# 🧪 Домашнее задание 6: Автоматическое тестирование

## 🔍 Контекст

**Asteroid Mining Corp.** вышла на орбиту! Приложение для управления миссиями по добыче ресурсов с астероидов активно используется — список астероидов отображается, ресурсы классифицируются, миссии запускаются. Команда продолжает развивать продукт: добавляет новые фичи, правит баги, рефакторит код.

Но с ростом кодовой базы стало заметно: каждый релиз — это лотерея. Одна «безобидная» правка может сломать карточку астероида, может поехать вёрстка диалога или перестать работать кнопка «Добыть». QA-инженер проверяет сценарии вручную, и каждый раз список проверок растёт.

### Функциональные требования к приложению

_(из общих требований проекта)_

1. **Список астероидов** — отображение астероидов с основными характеристиками (имя, диаметр, расстояние, ресурсы)
2. **Детальная информация** — модальное окно с подробными данными о ресурсах астероида (масса, объём, летучесть, порог сверхпроводимости)
3. **Классификация ресурсов** — визуальное различение типов ресурсов (минералы, жидкости, газы) по цвету иконки
4. **Добыча ресурсов** — кнопка запуска миссии с отображением состояния загрузки
5. **Навигация** — перемещение между разделами (Астероиды, План миссии, Статус добычи)

### Проблема

На последнем ретро команда зафиксировала:

- **Ручное тестирование не масштабируется** — при каждом изменении надо перепроверять всё приложение, что долго и дорого
- **Нет уверенности в BFF** — контракты с внешними API не проверяются, ошибки бэкенда обнаруживаются уже в браузере
- **Нет визуальной стабильности** — вёрстка «плывёт» незаметно, без очевидных ошибок в коде

### Решение

Команда решила внедрить **многоуровневое автоматическое тестирование**, которое закроет все слои пирамиды тестов:

| Уровень                    | Что проверяем                                                      |
| -------------------------- | ------------------------------------------------------------------ |
| **Тесты в памяти**         | Чистые функции, утилиты, хелперы — без дополнительных инструментов |
| **Юнит-тесты компонентов** | React-компоненты в изоляции — с помощью библиотек рендеринга       |
| **Юнит-тесты API**         | Эндпоинты/ручки BFF (Express) — с помощью HTTP-клиента для тестов  |
| **E2E**                    | Сквозные пользовательские сценарии в браузере                      |
| **Скриншотные**            | Визуальная регрессия                                               |

## 🎯 Задание

### Условие

#### Часть 0. Тестовые сценарии (документация)

Перед написанием кода составьте **тестовые сценарии** — список проверок для каждого функционального требования. Для каждого сценария определите:

- Что именно проверяется
- Какой тип теста подходит лучше всего (тест в памяти / юнит-тест компонента / юнит-тест API / e2e / скриншотный)
- Почему выбран именно этот тип

Сценарии оформите в папке `docs/`. Можно завести папку `docs/tests/` и описать тестовые сценарии в отдельных файлах.

#### Часть 1. Тесты в памяти

Напишите тесты в памяти для чистых функций и утилит приложения — **без дополнительных инструментов** (без рендеринга компонентов, без HTTP-запросов, без браузера).

**Примеры того, что стоит покрыть:**

- Форматирование чисел (функция `formatNumber` в `AsteroidDialog`)
- Определение типа ресурса (минерал / жидкость / газ) по набору полей
- Логика выбора цвета иконки ресурса (`ResourceIcon`)
- Валидация входных данных запроса на добычу (`validateMineRequest`)
- Любые другие чистые функции, которые вы найдёте или создадите в процессе рефакторинга

> 💡 Если логика «зашита» внутри компонента и не выделена в отдельную функцию — это повод для рефакторинга. Выделите чистую функцию и протестируйте её отдельно.

#### Часть 2. Юнит-тесты компонентов

Напишите юнит-тесты для React-компонентов в изоляции с помощью библиотеки рендеринга (например, React Testing Library).

**Обязательные сценарии:**

- `AsteroidCard` — рендерит переданные данные: имя, диаметр, расстояние, иконки ресурсов
- `AsteroidDialog` — открывается при вызове, отображает детальную информацию о ресурсах, закрывается по кнопке
- `ResourceIcon` — отображает правильный цвет в зависимости от типа ресурса (минерал vs жидкость/газ)

**Самостоятельные сценарии** — придумайте и реализуйте **минимум 2** дополнительных:

- Рендер `AsteroidList` с массивом астероидов
- Отображение навигационных ссылок в `Navigation`
- Состояние загрузки в `AsteroidMainBlock` (текст «Загружаем астероиды...»)
- `AsteroidDialog` при пустом списке ресурсов (отображение «Ресурсы не найдены»)
- _... или что-то своё_

#### Часть 3. Юнит-тесты API

Напишите юнит-тесты для эндпоинтов BFF (Express-приложение) с помощью HTTP-клиента для тестов (например, Supertest).

**Обязательные сценарии:**

- `GET /asteroids` — возвращает массив астероидов со статусом 200
- `POST /mine` — создаёт миссию по добыче при валидных данных
- `POST /mine` — возвращает ошибку при невалидных данных (пустой массив, отсутствие поля `asteroids`)

**Самостоятельные сценарии** — придумайте и реализуйте **минимум 1** дополнительный:

- Пагинация `GET /asteroids` (параметры `page`, `perPage`)
- Обработка ошибки при недоступности внешнего API астероидов
- Корректная работа middleware (логирование, обработка ошибок)
- Ответ при запросе на несуществующий маршрут
- _... или что-то своё_

#### Часть 4. E2E-тесты

Напишите сквозные тесты, проверяющие полные пользовательские сценарии в браузере (например, с помощью Playwright).

**Обязательные сценарии:**

- Пользователь открывает страницу и видит список астероидов с их характеристиками
- Пользователь кликает на карточку астероида и открывается модальное окно с детальной информацией о ресурсах
- Пользователь нажимает кнопку «Добыть» и видит индикатор загрузки

**Самостоятельные сценарии** — придумайте и реализуйте **минимум 1** дополнительный:

- Закрытие модального окна (по кнопке закрытия или клику вне окна)
- Навигация между разделами через меню
- Корректное отображение страницы при ошибке загрузки данных
- _... или что-то своё_

> 📌 E2E-тесты — это **сквозные** тесты: они должны проверять взаимодействие всех слоёв приложения (фронтенд → BFF → внешние сервисы). Убедитесь, что данные проходят через реальный (или замоканный) бэкенд, а не берутся из заглушки на фронтенде. Именно в этом ценность E2E — проверить, что все слои работают вместе.

> 📌 Обратите внимание на стабильность тестовых данных — используйте фиксированные данные или моки для предсказуемых результатов.

#### Часть 5. Скриншотные тесты

Напишите скриншотные тесты для проверки визуальной регрессии (например, с помощью Playwright).

**Обязательные сценарии:**

- Карточка астероида — внешний вид компонента
- Модальное окно с детальной информацией об астероиде
- Скриншот страницы или секции **с игнорированием области экрана**. Сделайте тест, который маскирует изменяющуюся область и сравнивает только стабильную часть контента

**Самостоятельные сценарии** — придумайте и реализуйте **минимум 1** дополнительный:

- Шапка сайта с навигацией
- Секция Hero
- Полная страница со списком астероидов
- _... или что-то своё_

> 📌 Для стабильности скриншотных тестов позаботьтесь о детерминированности: фиксированные данные, единый viewport. Эталонные скриншоты должны быть закоммичены в репозиторий.

> 💡 **Опционально:** для повышения стабильности скриншотных тестов можно отключить CSS-анимации и transitions перед снятием скриншота (например, через инъекцию стилей `* { animation: none !important; transition: none !important; }`).

### Требования к тестам

#### Читаемость кода

- Понятные названия тестов, отражающие суть проверки
- Логичная группировка тестов (по компоненту / фиче / уровню)
- Комментарии там, где логика неочевидна

#### Надёжность

- Тесты не зависят друг от друга и от порядка выполнения
- Используются моки и стабы для изоляции от внешних зависимостей (API, таймеры)
- E2E-тесты проверяют прохождение данных через все слои приложения

#### Оптимальность

- Для каждого сценария выбран минимально достаточный тип теста
- Нет дублирования проверок между уровнями
- Тесты проверяют поведение, а не детали реализации
