# Домашнее задание по инфраструктуре

В рамках домашнего задания должны быть настроены:

- CI/CD для проверки качества кода и автоматизации.
- Сборка Docker (OCI) контейнеров с возможностью локального запуска.
- Публикация frontend сборки на sourcecraft.site, которая использует общедоступный BFF в облаке.

## Список требований

- CI/CD
    - на все pull request должны запускаться:
        - проверка типов `tsc`
        - проверка качества кода `eslint` и `prettier` (либо как плагин ESLint)
        - запуск тестов `npm run test`
    - на все изменения в основной ветке `main` / `master` должны запускаться:
        - проверка типов `tsc`
        - проверка качества кода `eslint` и `prettier` (либо как плагин ESLint)
        - запуск тестов `npm run test`
        - проверка того, что проект успешно собирается, например, `npm run build`
    - при создании нового тега, который соответствует паттерну `v*` (например `v0.4.1`):
        1. проверка качества кода
            - проверка типов `tsc`
            - проверка качества кода `eslint` и `prettier` (либо как плагин ESLint)
            - запуск тестов `npm run test`
        2. создание релиза
            - с помощью API SourceCraft создаётся релиз с привязкой тега
            - заголовок и описание релиза заполняются на основании содержимого в файле `CHANGELOG.md` для указанного тега
        3. обновление ветки для сайта
            - из последнего релиза должна быть актуализирована ветка (`latest` или `release`) для сайта
            - запуск сборки проекта `npm run build`
            - исключение `dist` (директории со сборкой) из `.gitignore`
    - по расписанию запускаются
        - poor-man e2e тесты:
            - содержимое тестов может быть любым:
                - минимально: вызов `curl`, проверяющий, что сайт работает (этого более чем достаточно)
                - максимально: полноценные браузерные e2e тесты (Puppeteer, Cypress итп)
            - запуск каждый день в 12:00 по MSK
        - проверка устаревших зависимостей
            - запуск по вторникам и четвергам в 11 утра по MSK
            - запуск `npm outdated`
            - (дополнительно) спарсить вывод и отправить форматированное сообщение в Telegram Bot (токен доступа и идентификатор чата в секретах)
- сборка проекта (локальная)
    - frontend и backend части должны поддерживать изменение конфигурации на этапе сборки через переменные окружения или другие параметры
    - на frontend части:
        - версия приложения из `package.json` должна выводиться в футере рядом с копирайтом
        - URL для бэкенда может быть изменён на этапе сборки (натравить front на общий эталонный BFF)
    - Dockerfile для frontend (nginx)
    - Dockerfile для backend (node)
    - (дополнительно) используя `sed` и `entry-point.sh` сделать параметры изменяемыми в рантайме без пересборки
    - сконфигурирован `docker-compose.yml` файл
    - есть пример `.env` файла, переменные из которого используются в `docker-compose.yml`
- публикация сайта
    - должно соответствовать предыдущему в CI/CD
- настроить правила веток и тегов
    - теги `v*` не могут быть удалены
    - изменения в ветку по умолчанию `main` / `master` могут попадать только через pull request (уже настроено в шаблоне)
    - ветка, используемая для публикации сайта, не может быть удалена

## Тестовый BFF

Деплой реализуется только для frontend-части. BFF используется общий, уже доступный в облаке:

- `51.250.39.129:6678` [Swagger](http://51.250.39.129:6678/docs) / альтернативный `51.250.39.129:5678` [Swagger](http://51.250.39.129:5678/docs)
- WebSocket `51.250.39.129:5679` / альтернативный WebSocket `51.250.39.129:6679`

## Комментарии

Для проверки и отладки может быть полезен отдельный репозиторий (склонированный из рабочей ветки). Таким образом можно проверить положительные и негативные сценарии на pull request, правила для тегов и публикацию сайта.

Создавать теги можно через `git tag -a` либо `npm version`. Лучше использовать [`npm version`](https://docs.npmjs.com/cli/v8/commands/npm-version), так как в таком случае изменяется версия пакета в `package.json`.

Для управления конфигурацией frontend в рантайме достаточно иметь возможность кастомизировать URL BFF, версию приложения правильнее считать неизменной на этапе сборки. Ввести дополнительные параметры конфигурации (например, название компании или любые feature-флаги) можно по-желанию.

Вспомогательные скрипты можно писать на любом языке: где-то достаточно inline-bash, где-то можно использовать Node.

В CI проблемы с качеством кода не должны пропускать пайплайн до следующих шагов.

Дополнительно можно уделить внимание оптимизации: параллельное выполнение, кеширование и т.п.. Это дополнительное упражнение по-желанию.

Следите за безопасностью используемых секретов.
